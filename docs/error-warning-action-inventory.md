# Form action error and warning inventory

Recounted from route `actions` declarations, the `/app/[section]` delegation map, and the supplier action factory on 2026-09-26. This is a route-level inventory, not proof that every business branch has a final code. The “Role scope” column is a review target inferred from the action area; server guards and object scope remain authoritative. A mapped action still needs domain and browser verification before release.

**Count:** 180 named/default actions across 15 route patterns. The shared /app/[section] route delegates to the source action named in each row.

Current generic fallback means the body reaches `actionFailure` or its shared wrapper. This includes known business exceptions until their branch is mapped to a stable code. An empty explicit-key cell means the action delegates validation or returns another response shape.

## Current mapping audit

The shared `actionFail` path supplies a serializable code, parameters, field errors, remedies, and correlation ID. A code derived from a generic key does not prove that a known business blocker is explained. Known-error mappers cover listed repository messages; their final `actionFailure(error)` branch remains necessary for unforeseen exceptions. Those exceptions should keep the safe reference message. A known conflict that reaches that branch is a release gap.

The counts reflect a fresh source recount: 121 delegated `/app/[section]` actions plus 59 direct route actions, including 17 supplier factory actions, across 15 route patterns. They do not establish complete exception coverage. The penultimate numeric column counts direct `action.validation.*` literals in action bodies, not responses that users necessarily receive. The [finance action wrapper](../apps/portal/src/lib/server/actions/finance-actions.ts) replaces all 25 finance-module validation prechecks with action-specific typed problems before returning them; 22 of those paths are classified as approvals/finance and three worker-payment actions as billing/exports in this table. No other inventoried action body now has a direct `action.validation.*` response. Three additional `action.validation.*` strings in the expense detail route are comparisons used to normalize delegated failures, not direct responses. Thus 25 action paths contain direct literals and zero known validation prechecks return those literals after the wrapper. This does not prove that all known repository failures have precise messages. Raw bypass means a direct form action `fail(...)` that skips `actionFail` or shared `actionFailure`; the route search found none. The [billing email wrapper](../apps/portal/src/lib/server/actions/billing-actions.ts) calls SvelteKit `fail` while spreading a shared problem payload, so it is not counted as a bypass.

### Prioritized residual gaps

1. **Direct generic validation:** All direct schema and precheck branches in the inventoried actions now use typed problems at the response boundary. The 25 [finance](../apps/portal/src/lib/server/actions/finance-actions.ts) source literals are normalized at the exported wrapper. [Access](../apps/portal/src/lib/server/actions/access-actions.ts), [project/client](../apps/portal/src/lib/server/actions/project-actions.ts), [time](../apps/portal/src/lib/server/actions/time-actions.ts), [expense](../apps/portal/src/lib/server/actions/expense-actions.ts), [report/correction/planning/workforce](../apps/portal/src/lib/server/actions/operations-actions.ts), [billing](../apps/portal/src/lib/server/actions/billing-actions.ts), and [document](../apps/portal/src/lib/server/actions/document-actions.ts) action files have zero direct validation literals. Returned values exclude mailbox passwords. The owner administration profile, role-change, and offboarding validation prechecks now have stable codes, fields, retained safe values, and remedies. Owner administration browser evidence remains pending. Native mailbox creation failure has [wave-11 phone and desktop evidence](evidence/error-warning-wave11-manifest.md), including retained idempotency key and focused summary. Its [wave-8 browser manifest](evidence/error-warning-notification-recovery/wave-8-manifest.md) records 2/2 phone and desktop cases, including changed or unavailable records, retained filter/scroll, and cross-user denial.

4. **Field error language:** [The shared field renderer](../apps/portal/src/lib/portal/ui/form-validation.ts) translates common Zod diagnostics, then treats other raw text as a translation key. 5. **Remedy presentation:** [ProblemNotice](../apps/portal/src/lib/portal/ui/ProblemNotice.svelte) renders only server-permitted remedy IDs that the calling surface maps to a label or link. [ReportSection](../apps/portal/src/lib/portal/sections/ReportSection.svelte) and [PortalShell](../apps/portal/src/lib/PortalShell.svelte) now map the new report, planning, and skill remedies; the availability editor maps its date-review remedy. ## Recovery policy

Mechanical normalization (such as trimming harmless whitespace) and refreshing option lists may run without changing user intent. Retry a mutation only when an idempotency key proves it safe. For uncertain saves, inspect the created record before suggesting another submission. A stale record needs a review path and a description of the changed state. Never silently reopen a project, approve time, submit a draft, alter reimbursement or tax treatment, change an invoice, or overwrite another edit.

## Release audit

For each row, verify every known domain blocker has a stable code, localized cause, role-safe remedy, retained form values, and focused browser evidence. Unknown technical exceptions must show only a safe reference ID. “Generic fallback” is an audit cue, not a claim that every current fallback is a known business case.
