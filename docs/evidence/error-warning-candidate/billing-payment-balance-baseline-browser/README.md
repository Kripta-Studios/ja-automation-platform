# Stale invoice balance: browser baseline

Actual headless Chromium against isolated candidate commit `d06da2b62d53ac34abe5f83b30d80b3712de6646` on 27 September 2026. Playwright created a fresh disposable database with its synthetic issued invoice. Finance and Owner signed in through the rendered login form; each partial collection was entered and saved through the rendered payment form. This run did not contact production, send a payment, or change the shared repository.

The reproducible [browser case](baseline.spec.ts) passed **1/1**. It used an independent Finance context at **390 × 844, English**, and Owner context at **1440 × 900, Spanish**. It captured both native and JavaScript-enhanced action responses. See the [sanitized trace](results.json), [phone notice](finance-phone-390-en-notice.png), and [desktop notice](owner-desktop-1440-es-notice.png). The screenshots contain only the problem notice; the trace omits account identities, invoice identifiers, payment references, sessions, and raw response bodies. Both browser contexts had zero page exceptions and unexpected console errors.

| Case                    | Intervening authorized action                    | Stale submission                                                                      | Visible result                                                                                                                           |
| ----------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Finance phone, native   | Owner recorded a 1.00 partial collection         | Full balance from Finance's still-open form; HTTP 400 HTML                            | `BILLING_PAYMENT_AMOUNT_INVALID`; generic positive-or-excess wording, retained amount/reference, focused amount field; no second payment |
| Owner desktop, enhanced | Finance recorded another 1.00 partial collection | Full balance from Owner's still-open form; transport HTTP 200, action status 400 JSON | Same broad code with Spanish wording; retained amount/reference, focused amount field; no second payment                                 |

The failure cause is specifically **a balance reduced by another payment after the form opened**. The existing code and copy combine that case with zero or negative amounts and reversal limits. The response does not provide the newly available balance. The Finance native response rerenders the latest form maximum (79799.00 after a 79800.00 stale amount), while the Owner enhanced form still shows its old maximum (79799.00 after another 1.00 collection). In the Finance native case, window scroll moved from 1392 to 0; in the Owner enhanced case it stayed at 153. `focusTop`/`focusBottom` in the trace describe the **notice bounds**, while `focused` identifies the actual keyboard target. The enhanced notice was above the viewport at −552 to −380 px, although the amount field received focus.

The **Review invoice ledger** remedy is an in-page `#invoice-collections` link. Both clicks stayed in the same document and only scrolled the drawer. In the enhanced case the form maximum remained stale after clicking, and the old problem notice remained. A useful recovery needs to display the current balance and refresh the invoice data while keeping entered amount/reference, so another submit cannot rely on an outdated maximum.

The disposable fixture pointer and lock and port 4174 were released after the test. The run proves this two-role stale-balance case; it does not establish full Billing role or locale coverage.
