# Crew shared receipt allocation: stale-tab browser baseline

Product commit: `bcdd0fd9a9a1813751b256f5c9088f09778648a9`.

The tests use actual Playwright Chromium against a fresh disposable database. Owner creates a project and grants a chief two delegated workers through the rendered forms. The chief records both workers' time, then creates a draft worker-paid expense with a synthetic PDF receipt through the app. The chief opens the same Crew day in two tabs. Tab A selects the receipt and enters **7.00 + 5.50**. Tab B saves **8.00 + 4.50**. Tab A then sends its still-open values through an enhanced action-envelope probe and a native browser form submission. No production account, data, or deployment is touched.

| Viewport         | Stale response                                                                                                                                         | Visible result                                                                                                                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 390 px, English  | Native HTML **409** `CREW_RECEIPT_UNAVAILABLE`; enhanced HTTP 200 JSON envelope `type: failure`, `status: 409`, same code and `review_receipts` remedy | “The receipt is no longer an unallocated draft you entered. Review current receipts.” The “Review current receipts and allocations” link returns to this Crew date at `?review=1#crew-receipts`. The form, selected receipt, both checked rows, and both attempted amounts disappear. Saved allocation is visible below. |
| 1440 px, Spanish | Same native/enhanced status, code, and remedy                                                                                                          | “El recibo ya no es un borrador sin repartir que hayas introducido. Revisa los recibos actuales.” The same selection and amounts disappear; saved allocation is visible.                                                                                                                                                 |

The message does not say that a concurrent tab already saved the receipt, and it does not show the current **8.00 / 4.50** split beside the attempted **7.00 / 5.50** split. The persisted state stays at exactly one allocation group, two lines totaling 12.50, and one allocation audit event after both stale requests. No duplicate expense or allocation is created.

The problem notice receives focus and sits visibly below the header at y=86 on the phone and y=88 on desktop. Project, date, and locale remain selected. Scroll changes from 2361 to 194 on phone and 1424 to 168 on desktop; the user is moved away from the allocation section to the notice near the top. All three pages (Owner and two chief tabs) had no page exceptions or console errors.
