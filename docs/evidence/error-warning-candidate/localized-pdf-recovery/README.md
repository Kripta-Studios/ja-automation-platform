# Localized PDF recovery browser QA

Disposable Chromium exercised the real daily-report PDF panel and durable PDF jobs at 390 × 844 and 1440 × 900. The [test](../../../../tests/e2e/localized-pdf-recovery-browser.spec.ts) passed **2/2**. It made no production requests or writes.

| Scenario                                      | Browser and backend result                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accepted Generate response lost               | Spanish PDF POST persisted as 202. A collection GET reconciled the queued variant; Generate was disabled and the browser sent one POST.                                                                                                                                                                                                                        |
| Accepted Retry response and status check lost | A real failed render was retried once; the backend persisted 202, one retry decision, and attempt 2. The focused `LOCALIZED_PDF_RETRY_UNCERTAIN` notice explained the uncertainty and offered Refresh without displaying the stale Failed status. Retry stayed disabled. Refresh showed Queued without another retry POST.                                     |
| Ready download became stale                   | A Portuguese PDF reached Ready through the real worker. Its disposable file was removed while the browser still showed Download. The GET returned typed 409 `PDF_DOWNLOAD_INTEGRITY`; the backend quarantined the variant, recorded one integrity incident, and the focused notice showed Failed with Refresh and owner review guidance. Download disappeared. |

[Phone result](phone-390.json), [desktop result](desktop-1440.json), and redacted phone [retry](phone-390-retry-uncertain.png) and [download](phone-390-download-conflict.png) notice screenshots capture the visible wording, focus, status, response codes, attempts, and error counts. Console entries were the fixture-disabled offline identity 503, three deliberately aborted requests, and the expected 409; there were no page exceptions or unexpected HTTP errors. Matching desktop screenshots are included.

The first candidate showed the last known `Status: Failed` during an uncertain accepted retry. A fresh build with the status fix passed the direct absence assertion at both viewports; the redacted JSON and screenshots above were replaced by that run.

Command: `PATH=/opt/jaautomation/runtime/node-v24.19.0/bin:$PATH corepack pnpm exec playwright test tests/e2e/localized-pdf-recovery-browser.spec.ts --project=phone-390 --project=desktop --reporter=line`.
