# Operational option warning discovery in Chromium

Date: 2026-09-27. Baseline: isolated candidate commit `b19b3d4`. These are discovery results against two fresh disposable candidate databases using the rendered app in Chromium through Playwright MCP. They are not post-fix evidence and do not describe production. The first fixture had normal Owner, Manager, and Worker accounts; the second had no active Worker or Manager users and kept Owner active. No production records were changed.

## Checks

| Role / viewport / locale                                             | Observed behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker / 390 / EN                                                    | A direct link to a project outside the worker's assignments, while three other projects remained available, showed `OPERATIONAL_SELECTED_PROJECT_UNAVAILABLE` in Time, Expenses, and Daily Reports. The unavailable option remained selected and disabled; the date remained entered. Time and Reports focused the primary notice. The remedy was the role-safe instruction **Contact the project owner to review access.**                                                                             |
| Worker / 390 / EN / Expenses                                         | The same form also made an automatic `description-default` request for the inaccessible project. It returned HTTP 403 and added `EXPENSE_LOOKUP_DESCRIPTION_SCOPE_DENIED` below the primary notice. Focus moved to the second alert. This is a competing blocker for one known condition before submission.                                                                                                                                                                                             |
| Manager / 1440 / ES / Time                                           | An assigned worker with a date before the assignment start showed `OPERATIONAL_ASSIGNMENT_UNAVAILABLE_FOR_DATE`: “No hay ninguna asignación que cubra a este trabajador en esta fecha. Elige otra fecha o solicita que revisen la asignación.” The current project and **Activo** status appeared below it; remedy instructed the Manager to consult the owner. Changing the date into the assignment interval removed the warning and enabled the selected project without clearing worker or project. |
| Owner / 390 / PT / Time                                              | The same date conflict offered **Revisar atribuições**. The link prompted to discard the filled form, then opened the general assignment list at `/app/projects?action=update-assignment#project-assignment-list`, without selected project, worker, or date in the URL. The destination has an assignment section, but does not carry the form context.                                                                                                                                                |
| Owner / 390 / EN / Time                                              | With no active worker options, `OPERATIONAL_WORKER_OPTIONS_EMPTY` was focused and the worker selector had only its placeholder. **Review available workers** linked to `/app/profile`; clicking opened **Profile and security**, not worker administration.                                                                                                                                                                                                                                             |
| Owner / 390 / ES / Expenses; 1440 / PT / Daily and Technical Reports | The same no-worker code, role-specific translated text, focused notice, single worker placeholder, and `/app/profile` remedy appeared. The correct Owner team page at `/app/projects?view=team` displays **Team access**, **Create user access**, and **Include inactive specialists**.                                                                                                                                                                                                                 |

The no-worker remedy is a confirmed wrong destination in all three operational areas. The automatic Expenses lookup is a confirmed duplicate error and unnecessary 403. The broad Owner assignment destination needs a project-scoped recovery path if it is meant to help review the selected assignment. No form save was attempted for these pre-submit blockers. A Closing-project transition was not exercised in this bounded pass; the selected-project warning was triggered with a project outside the worker's assignments.

The browser console showed expected fixture `/api/offline/identity` HTTP 503 messages because offline mode was disabled. The Expenses 403 above was an additional, relevant request. No unrelated form JavaScript exception was observed. Screenshots crop warning notices only and show no account credentials, session values, record IDs, or full request bodies.

Evidence: `results.json`, `worker-time-project-phone-en.png`, `manager-time-date-desktop-es.png`, `owner-reports-no-workers-desktop-pt.png`.

## Independent post-fix pass

The repaired candidate was checked in two **new** disposable fixtures after the focused suite passed 8/8. This pass used the reviewed but uncommitted three-file operational overlay on base `b19b3d4`; it does not replace the baseline discovery above.

| Role / viewport / locale           | Observed result                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker / 390 / EN / Expenses       | Direct-linked unavailable project still shows `OPERATIONAL_SELECTED_PROJECT_UNAVAILABLE` with its disabled selected option. A typed amount, description, and changed date remained in the form. No `description-default`, crew-worker, or linked-time API request was made for that unavailable project; no Expense 403 or competing lookup notice appeared. The primary notice received focus on form open. The only other notice was the expected payer-treatment warning. |
| Owner / 390 / ES / Time            | The date-specific assignment warning linked to `/app/projects` with the selected project, worker, locale, and `update-assignment` action in the URL. After accepting the intentional Spanish unsaved-changes confirmation, the destination showed one matching assignment row in **Actualizar asignación**. The section received focus and the document stayed within 390 px.                                                                                                |
| Owner / 390 / EN and ES; 1440 / PT | Time, Expenses, Daily Reports, and Technical Reports linked `OPERATIONAL_WORKER_OPTIONS_EMPTY` to the locale-preserving Team access specialists anchor. The warning received focus before navigation. Clicks from Time, Expenses, and Technical Reports reached the translated Team page with Create user and inactive-specialist controls.                                                                                                                                  |

One navigation accessibility issue remains for the Team remedy destination. At 390 px in ES and 1440 px in PT, `SECTION#team-panel-specialists` has no `tabindex`, focus stays on `BODY`, and the anchor scroll places the section at roughly 0.47 px from the viewport top. Its heading starts at 42.56 px, behind the sticky header ending at 69.59 px on phone and 72 px on desktop. A follow-up focus/scroll-margin fix is required before this remedy is fully usable by keyboard and sighted users.

Current-navigation console showed the disposable fixture's unrelated `/api/offline/identity` HTTP 503. No Expense API 403 was observed in the post-fix flow. See `postfix-results.json` and `postfix-worker-expense-project-phone-en.png`. The screenshot crops only the notice.

## Team destination focus retest

A further Team anchor focus and scroll fix was checked in a third fresh no-worker disposable fixture. From Expenses at 390 px in ES and Technical Reports at 1440 px in PT, the no-worker notice was focused before navigation. Each locale-preserving remedy reached Team access through an HTTP 200 data request. `SECTION#team-panel-specialists` now has `tabindex="-1"` and receives keyboard focus. Its top is 88.47 px and its heading starts at 130.56 px, below the sticky header ending at 69.59 px on phone and 72 px on desktop. Translated Create user and inactive-specialist controls remain present; document widths match the viewports. The current console showed only the fixture's unrelated offline-identity 503, and no Expense lookup request occurred in the ES case. This resolves the destination issue recorded above. See `focus-retest-results.json` and the cropped, identifier-free `focus-retest-team-heading-pt.png`.
