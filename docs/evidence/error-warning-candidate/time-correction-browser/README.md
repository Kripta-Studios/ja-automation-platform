# Time correction duplicate draft: actual browser race

**Environment:** local portal preview with a fresh, disposable Playwright database. The Owner and Worker signed in through the rendered login form. Database fixture code created only the prerequisite synthetic project and Worker assignment. The Worker created and submitted the original time entry through the form, and the Owner approved it through Approvals. Two Worker tabs then made separate correction attempts through the rendered correction form. No production records were touched. Cropped screenshots contain only the notices; no session data or record identifiers are retained.

The 409 notice explains that an active correction draft now exists and offers **Review updated time entry** (localized for ES/PT). It shows the current Approved status. After the stale submission, the correction form is removed and a recap shows the attempted activity summary, reason, 195 actual minutes, and site. The new correction remains the only linked correction row. The notice takes keyboard focus and is wholly visible at all checked widths; there is no horizontal overflow or JavaScript page exception. The Owner approval occurred through the UI in each run. The candidate did not reopen or overwrite the approved original.

The attempted form was scrolled before submission (about 700–1,000 px, depending on width). The notice is near the top of the response, so the browser scrolls to 0 to show the focused problem. This check proves visible focus and retained values; it does not prove exact scroll-position restoration. The Portuguese screenshot at `f869235` uses both “registo” and “registro” in body and remedy text. A later catalog-only commit, `d809386`, aligned this wording; that commit was not browser retested in this packet.

Evidence is in `baseline-e645694-*-results.json`, `*-results.json`, and the matching cropped `*-duplicate-notice.png` files. The executable [browser spec](candidate.spec.ts) uses real UI actions for the correction race. Baseline and fixed runs each passed two viewport tests; the Portuguese follow-up passed one test. The JSON includes redacted response status, code, route, locale, focus and viewport observations. These were actual server conflicts, with no intercepted responses.
