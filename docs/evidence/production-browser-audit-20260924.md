## Método y protección de datos

- Todas las operaciones de negocio se hicieron mediante controles visibles de Chromium con Playwright: formularios, selectores, adjuntos, botones y enlaces. Las consultas a SQLite fueron solo de lectura para corroborar persistencia. No inserté ni modifiqué datos de negocio por SQL o API.
- El usuario autorizó expresamente tiempos, gastos y cobros ficticios y el uso de la cuenta Owner suministrada. Actividades, nombres y referencias QA indican que no hubo trabajo ni transferencia bancaria real. No se envió correo a terceros.
- El usuario autorizó inventar los datos de emisor y numeración QA. La revisión canónica usa un identificador fiscal ficticio (QA-NOT-REAL-20260924), dirección ficticia y nombre marcado FICTIONAL. El campo obligatorio «Accountant approved at» recibió una fecha simulada. Esto **no prueba verificación fiscal ni aprobación contable real**. Las facturas emitidas y cobros QA permanecen en producción como historia sintética y no deben interpretarse como operaciones reales.
- Sesiones, capturas, PDFs y ficheros de prueba están en /home/kripta/production-browser-audit-20260924/, directorio privado 0700; los estados de sesión tienen permisos 0600. No se publican contraseñas ni tokens.
- Tras varios inicios de sesión apareció «Too many sign-in attempts». A petición expresa del usuario se adelantó **una sola vez**, por código, el inicio del contador de 15 minutos a las 17:22:01 UTC; la ventana original había empezado a las 17:07:44 UTC. Fue una excepción para empezar la auditoría. Después se usaron sesiones persistentes.
- WebKit se usó para compatibilidad básica; no equivale a Safari en un iPhone o iPad físico.
